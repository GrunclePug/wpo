# T3 backend and compatibility

T3 is the default execution backend. WPO keeps its existing Python scheduler, gates, data formats
and dashboard; a durable coordinator bridge executes model sessions using native `delegate_task`.
Read [t3-bridge.md](t3-bridge.md) before attaching a repository or processing a backend control wake.
The standalone subprocess backend remains available through explicit machine configuration.

Native task execution requires a live provider-owned T3 parent run. External MCP owner tokens and
the Python daemon cannot satisfy that requirement. The bridge uses T3's supported CLI only to
wake an attached existing coordinator, then native tools execute every requested model task.
It does not scrape credentials, create shell worktrees, or fall back to standalone models.

| Capability | T3 backend behavior |
|---|---|
| WP files, dependencies, statuses, lane scheduling/holds/pools/limits | Existing scheduler and formats retained. Enabling T3 or attaching never resumes holds. A pool whose provider is disabled remains unroutable. |
| Checkout preparation and base | Native isolated WP coordinator task owns the checkout. Registration validates repository/common gitdir, actual branch and expected local-main ancestor; later use revalidates identity. |
| Existing in-flight WPs | First authorized run non-destructively imports legacy committed/staged/dirty/untracked work. Original checkout remains intact. Conflicts or partial import require reconciliation. |
| Builder/review rounds, findings/vetoes, re-evaluation/escalation/split | Existing runner and findings protocol retained; each model session is a fresh native delegated task. |
| Verify, autofix, build slots, ownership, scoped/workspace checks | Existing commands and gates retained. Native task prompts include explicit session identity. Read-only/scoped role mutations are checked afterward without destructive rollback. |
| Repair, interruption recovery, handoffs | Existing ledgers/recovery reports retained. A provider continuation is a fresh native task using persisted WP/handoff/diff context, not a claimed native conversation resume. |
| Delegated workers and staged plans/executors/assembler | Existing CLI/state contracts retained. Native scoped sessions serialize within a WP checkout; the lead must stop writing during workers. Different WP lanes remain parallel. |
| Optional in-session helpers | `session_workers` resolves an explicit live native helper target, including effort and family availability. Native helpers replace CLI agent definitions and remain within the lead's ownership/verification responsibility. |
| Model tiers, effort, pinning and fallback | Existing router selects routes. Configured aliases map explicitly to recorded live native IDs/options. Unsupported/disabled providers/models/efforts are skipped with reasons, never replaced by a CLI backend. |
| Subscription quota and burn forecasting | Existing external usage adapter/cache/history and quota policy retained. Cutoffs queue native cancellation; handoffs queue a native steer. The coordinator itself also needs available quota. |
| Context/compaction control | Real native callbacks can trigger existing handoff/staged-compaction handling. T3 does not expose universal continuous telemetry or provider compaction overrides; hard pre-compaction interception cannot be promised. |
| Events and unattended attention | Existing append-only journal retained. Attached coordinators receive debounced durable attention requests; identical repeated reasons do not trigger repeated model wakes. |
| Messages, pause/wrap-up and cancellation | Existing inbox/holds retained. Native steer/cancel requests execute through the coordinator. Message files are marked delivered only after native success. |
| WPO command approvals | Existing files/dashboard actions retained. Native T3 permission prompts remain native and must be answered there; WPO approval cannot authorize them. |
| Dashboard, session views, request placement and audit | Existing views/actions remain, plus native request/task links and explicit recovery. Placement/audit sessions are fresh native tasks. No polling of running native task status. |
| Logs, usage and costs | Old logs remain readable. New native results are normalized to existing JSONL with additive metadata. Actual usage callbacks are included; missing telemetry is marked unparsed rather than reported as free. |
| Restart/reconnection/liveness | Durable request IDs, generation receipts and native task IDs survive Python restarts. Missing progress becomes stalled; explicit recovery wakes once. No blind relaunch or paid per-loop wake. |
| Integration and cleanup | Existing verified fast-forward integration uses actual native branch mapping. WPO retains T3-owned directories/branches and cleans only separately configured build output. |
| Permissions/tool allowlists | T3 providers enforce their native permission modes. WPO's exact legacy per-command tool sandbox is not available through native delegation; explicit role contracts plus mutation gates provide a narrower check, not equivalent sandboxing. |

The matrix describes implemented behavior and its actual boundaries. Enabling a disabled provider,
supplying a usage adapter, attaching an available coordinator, or reconciling a stale native task
may still be necessary on a particular installation. The current live capability record, rather
than a bundled model snapshot, determines which native models can run.
